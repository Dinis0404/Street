## 一、願景與目標

把現有的單一場景引擎，升級為能承載「整個街區」的開放世界街道模擬器：

1. **範圍**：完整復刻臺北市信義區核心範圍——從台北 101、四四南村的經典打卡視角，到吳興街巷口的傳統店家，總可漫遊面積約 **2.4 km × 2.0 km**。
2. **精細度**：核心商圈逐窗、逐招牌對照實景還原；次要街區保證體量、樓層、招牌、路樹、機車密度等「臺北感」成立。
3. **動態**：沿用現有晝夜＋天氣系統，新增車流、行人、跨年煙火等城市生命感系統。
4. **驗收方式**：沿用本專案既有工作流——**每個街區都要與實景照片逐格比對修正**（如先前河口湖店面的做法）。
5. **技術底線**：維持純靜態網站、零 build 步驟、完全離線可玩（three.js 內建於 `libs/`，部署 Vercel / GitHub Pages 零設定）。

### 2.2 現有架構瓶頸（必須解決，否則無法承載街區）

| 瓶頸 | 現況 | 後果 |
| --- | --- | --- |
| 場景寫死在單檔 | `world.js` 1005 行，所有物件以程式碼逐個建立 | 無法管理數千棟建築 |
| 無串流機制 | 一次性建好全部場景 | 信義區規模會直接凍結頁面 |
| 無 LOD | 每棟樓都是全細節 | 遠處數千樓吃滿三角形預算 |
| 無 Instancing | 同類物件各自獨立 mesh | 數千機車/路燈會產生上萬 draw call |
| 碰撞為線性陣列 | `colliders` 陣列逐一比對 | 數千碰撞體時幀率崩潰 |
| 地面高度硬編碼 | `groundHeightAt()` 用 if 座標判斷 | 無法支援空中走廊、階梯、山坡地 |
| 無除錯工具 | 無自由飛行相機、無效能面板 | 大場景製作與除錯困難 |

## 三、範圍定義

### 3.1 世界座標與比例

- **比例**：1 單位 = 1 公尺（與現有場景一致）。
- **原點**：台北 101 塔樓中心，實際座標 `(25.0338°N, 121.5647°E)`。
- **軸向**：`+x` = 東、`-z` = 北、`+y` = 上（沿用現有場景「-z 為北」的慣例）。
- **投影**：實際經緯度以本緯度（約 25°N）等距換算——緯度 1° ≈ 111,320 m、經度 1° ≈ 100,980 m。街道真實斜向角度由 OSM 座標自動帶入，**不做網格矯正**。
- **世界邊界**：可玩範圍約 `x ∈ [-1100, 1300]`、`z ∈ [-1000, 1000]`，邊界以圍籬/綠帶收邊，超出部分為靜態背景。

### 3.2 三層範圍（分級製作）

| 層級 | 範圍 | 製作密度 |
| --- | --- | --- |
| **Tier 1 核心商圈** | 信義計畫區：忠孝東路五段以南、信義路五段以北、松仁路以東、基隆路一段以西（約 0.9 × 0.9 km） | 逐窗逐招牌還原，S 級 |
| **Tier 2 延伸街區** | 國父紀念館、松山文創園區＋大巨蛋、四四南村、吳興街商圈、永吉路、五分埔、松山路沿線、台北機廠、捷運站周邊 | 體量＋招牌＋街道細節，A 級 |
| **Tier 3 背景層** | 象山山體與步道、大安/松山/南港方向遠景樓群、101 觀景塔尖 | 剪影＋霧氣，B 級 |

### 3.3 還原度分級標準

| 等級 | 定義 | 驗收門檻 |
| --- | --- | --- |
| **S** | 建築逐層樓高、窗帶、入口、招牌、廣告牆、夜間照明全部對照實景 | 至少 3 張不同角度實景比對圖通過 |

## 六、技術架構升級

### 6.1 總原則

1. **零 build、純靜態、離線可玩**——所有資料以 JS 模組存放，所有貼圖程式生成或打包為 PNG 靜態檔。
2. **資料驅動**——街廓由資料檔描述（footprint、樓高、招牌），程式只負責「生成器」；地標級建築才手寫專屬建構器。
3. **每幀可預算**——串流建構限時（每幀 ≤ 4 ms 工作預算），避免卡頓。

### 6.2 目標模組結構

```

  systems/

    nightlights.js    # 夜間燈光註冊表（自 glow.signMats 泛化）
    traffic.js        # 車流 AI
    npc.js            # 行人 AI
    fireworks.js      # 跨年煙火
    minimap.js        # 小地圖＋快速傳送
  city/
    city.js           # 城市總管：分派 chunk 建構、串流佇列
    chunk.js          # 150m 區塊：建構/啟用/休眠/釋放
    ground.js         # 地面、人行道、可走面系統

    props.js          # 街道小物（InstancedMesh 群組）

    vehicles.js       # 車輛模型工廠
  landmarks/          # S 級地標專屬建構器
    taipei101.js  cityhall.js  memorialhall.js  mall-a8a9a11a4.js
    breeze.js  nan-shan.js  sisy-village.js  dome.js  songyan.js ...
  data/
    district.js       # 分區/街廓/道路資料（OSM 生成＋手工校訂）
```

### 6.3 區塊串流（Chunk Streaming）

- 區塊尺寸 **150 m × 150 m**（核心區約 170 塊，全區約 230 塊）。
- 每塊四狀態：`queued → building → active → dormant`；以玩家位置為中心，半徑 450 m 內 active、之外 dormant（隱藏並釋放幾何，材質/貼圖留快取）。
- 建構走優先佇列（距離近優先、視線錐內加權），**每幀限時 4 ms**，逐幀消化。
- S 級地標不串流——預載並常駐（101 等遠觀地標反而在遠處也要可見）。

### 6.4 Instancing 清單

機車、路樹、路燈、紅綠燈、冷氣室外機、水塔、阻車柱、花圃盆栽、垃圾桶、變電箱、郵筒、YouBike 站柱、交通錐、行人（近景少量）。目標：**全城靜態物體 draw call ≤ 400**。

### 6.5 LOD 三級

| 級別 | 距離 | 內容 |
| --- | --- | --- |
| L0 近景 | < 90 m | 全細節：門窗框、招牌、冷氣機、屋頂雜物 |
| L1 中景 | 90–300 m | 簡化立面＋窗帶貼圖（含夜間窗光貼圖） |
| L2 遠景 | > 300 m | 純量體＋單張立面貼圖＋屋頂色塊 |

切換加滯回（hysteresis ±15 m）避免邊界閃爍；地標採自訂三段 LOD。

### 6.6 貼圖策略

- 貼圖工廠 2.0：按**材質家族製作圖集**（facade 圖集、人行道圖集、招牌圖集、屋頂圖集），同一圖集內物件合併幾何，壓低材質切換。
- 全域貼圖快取（key → texture），chunk 休眠時貼圖不釋放。
- 中文字型鏈：`"Microsoft JhengHei", "PingFang TC", "Noto Sans TC", sans-serif`。
- 大型電視牆/廣告用 `texture.offset` 動畫，不重繪 canvas。

### 6.7 光照與夜間城市燈光

- 單一方向光（太陽/月亮）＋半球光沿用；**陰影相機跟隨玩家**（200 m 範圍，手機 1024/桌機 2048）。
- 夜間沿用「emissive ＋ bloom」策略（不靠真實點光源），真實點光源僅保留**玩家周邊最近 6 盞**路燈池（沿用現有機制泛化）。
- 夜間燈光註冊表：所有需要晝夜切換的材質登記 `{day, night} emissive` 插值對（現有 `userData.day/night` 機制抽出全域化）。

### 6.8 碰撞與可走面

- 碰撞體放入**空間雜湊網格**（cell 20 m），查詢 O(1)。
- 可走面系統取代 `groundHeightAt()` 硬編碼：地面區域多邊形（人行道/廣場/山坡步道）＋**空中走廊平台與樓梯/坡道**查詢，支援高架行走與上下樓梯。

## 七、資料管線

### 7.1 底圖資料（一次性生成腳本）

```
工具/scripts/build-district.mjs     # Node 腳本（一次性，不隨遊戲發布）
  1. Overpass API 抓取範圍內 OSM：building footprint+height+levels+name、
     highway 路網+车道、park/water、shop/amenity POI
  2. 投影至世界座標（§3.1），依 150m 網格切塊
  3. 輸出 js/data/district-*.js（含 ODbL 出處註記）
```

- 建物高度缺漏時以樓層數 × 3.2 m 推估，再以政府開放資料（臺北市建物相關開放資料集）與實景照片人工校訂。
- S 級地標在資料檔中標記 `override`，由 `landmarks/` 專屬建構器接管，不走通用生成。

### 7.2 實景參考庫

- `docs/refs/<街區>/`：每街區收錄 3–10 張實景參照截圖（街景/實拍），標註方位與比對點。
- 參考照片**僅供比對**，不直接作為貼圖素材（著作權考量，見 §11）。

### 7.3 手工校訂迴圈

資料檔即手工編輯介面——除錯相機走查 → 比對照片 → 直接改資料檔座標/樓高/招牌 → 熱重載（開發模式保留 URL 參數重載單一 chunk）。

## 九、效能預算

| 指標 | 桌機（60 fps） | 手機（30 fps） |
| --- | --- | --- |
| 可見 draw calls | ≤ 900 | ≤ 350 |
| 可見三角形 | ≤ 2.5 M | ≤ 0.9 M |
| 貼圖記憶體 | ≤ 1.2 GB | ≤ 400 MB |
| 串流建構 | ≤ 4 ms/幀 | ≤ 2 ms/幀 |
| 陰影解析度 | 2048 | 1024 |
| Bloom | 開 | 關 |

優化手段優先序：frustum culling（內建）→ chunk 距離休眠 → Instancing → LOD → 圖集合併 → occlusion（最後手段，僅 101 裙樓等大遮蔽體）。遊戲內建效能面板持續驗證。

## 十一、風險與對策

| 風險 | 等級 | 對策 |
| --- | --- | --- |
| 商標/著作權（連鎖店招牌、101 商標、參考照片） | 高 | 招牌全部**風格化仿製**（配色/構圖像但字樣自創或通用化）；照片僅比對不取材；README 註明「粉絲重現、與各商標權利人無關」 |
| 規模失控（信義區範圍太大做不完） | 高 | §3.2 分層制度——任何階段停在「量體＋路網」都是可玩狀態；P1 結束即有最小可玩版本 |
| 效能崩潰 | 中 | §9 預算制＋效能面板常駐；每階段驗收含效能門檻 |
| OSM 資料品質（樓高缺漏、footprint 誤差） | 中 | 手工校訂迴圈（§7.3）；地標一律 override |
| three.js r149 停在舊版 | 低 | 維持 r149（升級觸碰色彩管理/大量 API 變更，成本高收益低）；僅在需要特定新功能時再評估 |
| 瀏覽器記憶體（長時間漫遊） | 中 | chunk dormant 時徹底 dispose 幾何；貼圖快取上限 LRU |
| 中文字型跨平台渲染差異 | 低 | 字型鏈 fallback＋招牌貼圖快取 |

## 十二、總驗收標準（Definition of Done）

1. **比對**：核心商圈 12 個指定比對點（路口/地標各角度）實景照片 side-by-side 檢查通過。
2. **效能**：桌機 60 fps／手機 30 fps 達標，載入不凍結主執行緒。
3. **完整體驗閉環**：開場 → 選地圖 → 落地四四南村 → 走空中走廊 → 登象山看夜景 → 觸發跨年煙火，全程不掉幀、不穿牆、不卡死。
4. **細節清單**：§5 八類細節達成率 ≥ 90%，未達成項目列明原因。
5. **離線與部署**：拔網路線可玩；Vercel/GitHub Pages 零設定部署。
